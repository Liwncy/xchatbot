# 方案：按聊天记一张会过期的记忆卡

状态：worker 已上线，整理在一个真实群里跑过。系统提示里换卡这一步还没在真的 dsh 里看过（第 10 节）。不安装 SurfCore，不改它的预设和 MCP。

一个聊天一直用现在这场 DSH 会话，对话留在里面。记忆是这场会话外面的一块，由 xchatbot 拿着。每次模型开口前，把**现在这一块**和这场对话拼在一起。内容更新了，下一次拼的就是新的。旧的不写进对话记录。

这一块有两层：

- **房间卡**：这个群或这段私聊共用的。口头禅、对整个聊天的约定、不指向某一个人的事。
- **此人卡**：只记眼前这个发言人。谁发言就拼谁的；别人的不带。**卡跟着人走，不跟着聊天走**：同一个人在哪个群、在私聊里，用的是同一张。第一版是按聊天分开的，后来改成共享，见第 10 节的隐私一条。

不换会话。不把卡抄进每一条微信入站。

## 1. 各管一段

| 层 | 在哪 | 给模型看什么 |
|---|---|---|
| 原文 | `chat_message` | 不自动看。更早的仍走 `agbot_chat_history` |
| 房间卡 | xchatbot，按 `session_id` | 这个聊天还留着的共用印象 |
| 此人卡 | xchatbot，按 平台 + 发言人，不分聊天 | 眼前这个人的印象，在哪个聊天说话都是这一张 |
| 近窗 | 入站 `## 上下文` | 近 10 分钟、最多 15 条入站，照旧 |
| 本段对话 | 当前这条 DSH 会话 | 从开这场到现在说过的话，接着用 |

卡的内容、衰减、版本都在 xchatbot。Harness 只负责在每次请求前把「房间卡 + 当前发言人的卡」放进这场会话的系统提示。近窗里其他人的印象不额外拼。OpenClaw、Hermes、QwenPaw、蜗牛没有这场我们拿得到的系统提示，这一步先不接。它们仍只收现在的入站正文。

## 2. 范围

做：

- 房间卡按 `chat_message.session_id`。群是房间 id（`resolveChatSession` 里群的 `chatId`），私聊是 `private:` 加对方 id。
- 此人卡按平台加发言人 id（入站里的 `from`）。不分聊天：存在 `chat_memory` 里，`session_id` 固定是 `@people`，`subject` 是 `golem:wxid_…` 这样的 `平台:发言人 id`。机器人自己的发言不建此人卡。
- Harness 在该 agent 的 `systemPrompt.section` 上挂一节。`text` 用函数，每次组装系统提示时现算，返回这一刻的房间卡和当前发言人的卡。
- 拼出来的正文变了（房间卡变了、发言人换了、或这个人的卡变了），下一轮请求替换系统提示开头那一格，并清掉本场里后追加的系统提示。用户消息和助手回复不动。

不做：

- 不写进 `buildInboundContent`，不进 `## 上下文`，不进 `followup` 的用户消息。
- 不用 `systemPrompt.context`。那个会变成用户消息快照，留在对话记录里。
- 不因为记忆换 DSH 会话，不加轮数上限。会话 id 仍是现在的 `xbot-${safeId(chatId)}-v2`。
- 房间卡不跨聊天：A 群的梗不会出现在 B 群。人的卡才跨聊天。
- 不做向量检索，不做第二份全量档，不做 `#记忆` 口令。
- 不扫 `chat_message` 找「哪些会话要整理」，也不为了找人再扫一遍。
- 不在这一步打开 `wrangler.toml` 的 cron。`crons` 保持 `[]`。

## 3. 卡怎么进模型

DSH 的 `PromptSection.text` 可以是函数，每次 `assemble` 才执行。Harness 在这条 agent 上注册一节，名字固定，例如 `xbot-memory`。函数读本机记下的房间卡，以及**这一轮发言人**的此人卡。某一层是空的就略去，两层都空则这一节不出现。

入站 JSON 增加这些字段，都不进入模型正文。发言人沿用已有的 `from`。

- `logSessionId`：`resolveChatSession` 的 `session_id`。Harness 不要用自己的 `chatId` 去猜。
- `roomRev`：房间卡正文的哈希。没有就是 `""`。
- `speakerRev`：这个 `from` 的此人卡哈希。没有就是 `""`。别的聊天里整理改了这张卡，这里的版本号也会变。

每一轮开始时，本机按 `chatId` 记房间卡，按 `chatId` + `from` 记此人卡。

| 情况 | 动作 |
|---|---|
| `roomRev`、`from`、`speakerRev` 都和本机已挂上的一致 | 只 `followup` 入站正文 |
| 任一层变了，或这个人的卡还没取过 | 向 worker 取房间卡和这个人的卡，换上这一节，再 `followup` |
| 取卡失败，或入站没带 `logSessionId` | 房间卡用本机记着的；此人卡只用本机记着的**这个人**的，没有就不带。不沿用上一个发言人的 |

缓存只在 dsh 进程的内存里，不落文件。dsh 的工作目录就是模型能读写的那个目录，落在那里等于把所有聊天的卡摆给模型翻。重启后本机是空的，下一条带着非空版本的入站会再向 worker 取。

DeepSeek 这条路线的系统提示更新是 `in-history`：同一场请求序列里，系统提示变了会再追加一条，旧的还在。拼出来的正文和上一轮不同时，要把这次请求标成新序列（`agent/pre-step` 的 `startsRequestSeries`）。这样 DSH 会改掉系统提示头节点，并清空后面追加的系统提示。对话记录不动。正文没变不要标。发言人换了也算正文变了：换掉的是系统提示里的那一格，这场会话照旧接着聊。

正文告诉模型：房间卡是这个聊天还留着的印象；此人卡只关于眼前发言的人，他在别的聊天里也是这样，但他在别的聊天里的事不要主动提起。都不是刚发生的事。别复述。和眼前对不上时以眼前为准。

## 4. 卡里有什么

条目是源，正文由条目渲染。模型只看见渲染结果。

```json
{
  "id": "稳定 id，合并时用来认同一条",
  "kind": "见下表",
  "text": "一句人话，不超过 40 字",
  "pin": false,
  "clarity": "clear | fuzzy | trace",
  "createdAt": 0,
  "lastSeen": 0,
  "importance": 40,
  "recallCount": 0,
  "retention": 0
}
```

`createdAt` 是记下它的时刻，`lastSeen` 是最后一次被提到，`importance` 创建时算好后不变，`recallCount` 是被提到过几次，`retention` 是上次整理算出的保留分，只用来排序。这几项都在 `items_json` 里，不改表；老条目缺的项在读出时补默认值（重要度 40，约定 56，创建时间取最后提到的时间）。

房间卡：

| kind | 记什么 |
|---|---|
| `promise` | 小聪明儿自己答应这个聊天、之后真要去做的事 |
| `bit` | 这个聊天的口头禅、梗 |
| `fact` | 不指向某一个发言人的事 |

指向具体的人的句子放进此人卡，不留在房间卡。

此人卡：

| kind | 记什么 |
|---|---|
| `person` | 是谁、怎么称呼、说话习惯 |
| `promise` | 小聪明儿答应这个人、之后真要去做的事 |
| `first` | 在这个聊天里第一次怎么认识。一个人只留一条，有了就不再收新的 |
| `preference` | 他的偏好、忌讳 |

「约定」的口子要窄：群友之间的约定、玩梗、演戏、斗嘴放的狠话都不算，哪怕是小聪明儿自己说的；值得记就归到 `bit` 或 `person`。第一次在真实群里整理时没写这一条，模型把斗嘴的狠话全当成约定。

### 重要度和淡忘

**分工**：模型只说「新冒出来什么、归哪一类、该记多久（`weight` 1-3）、哪几条又被提到了」。重要度怎么算、淡多快、钉不钉、满了丢谁，都由代码按固定公式算。公式和数字照 SurfCore 的 `targetClarity` 搬过来，在 `card.ts` 的 `FADE` 里，要调快慢改那一处。

**起点分**（创建时算一次）：

| 来源 | 分 |
|---|---|
| 模型 `weight` 1 / 2 / 3 | 20 / 40 / 60。没写或写歪了按 1，超出范围夹回 1-3 |
| 种类是 `promise` | +16 |
| 在主人自己那张此人卡里 | +32 |

模型最高只能给到 60，再高必须靠代码认得出的信号（主人、约定）。钉住只看种类：只有 `first` 钉住，永远在。模型输出里没有 `pin`。

**保留分**（每次整理都从头算，不记「昨天降到哪了」）：

```text
保留分 = 重要度
       + 被提到次数 × 2（最多 +12）
       + 记下不到 7 天：+18
       + 最近 2 天内被提到：+8
       − (年龄 − 7 天) × 0.35（最多扣 80；主人的重要条目按 0.12）
主人的重要条目（主人卡里、重要度 ≥ 65）：保底 55
记下不到 7 天：保底 50
```

| 保留分 | 样子 |
|---|---|
| ≥ 46 | 清楚 |
| 24 – 46 | 模糊 |
| 12 – 24 | 痕迹 |
| < 12 | 从卡上拿掉 |

另有一条：记下超过 60 天、重要度低于 50、又不是主人的重要条目，直接拿掉。

按这个算，不被再提的条目大致能留：权重 1（20 分）约 30 天，其中前 7 天清楚，之后只剩痕迹；权重 2（40 分）到第 60 天；权重 3（60 分）要过 100 天。主人卡里重要度 65 以上的，几百天后仍是清楚。约定比同权重的梗多 16 分。原文还在 `chat_message`（只留 30 天）。

**因为每次都从头算**，整理跑几次、隔多久跑都不影响结果，停几天再跑也不用补。和 SurfCore 的差别：它每天只往目标档位挪一格，我们直接算到目标。

**又被提到**只有两种情况会生效：模型把旧条目的 id 写进 `seen`，或者带着原 id 改写了它。效果是 `lastSeen` 变新、`recallCount` 加一，在公式里最多是几分的加成，救不了过期的低分条目。**模型把旧条目原样抄回来不算。** 第一版的规则是「模型带回来的就算还在用」，结果模型每次都原样全抄，所有条目永远是清楚的，卡根本不会过期；现在即使它把所有旧 id 都报进 `seen`，也只是淡得慢一点。

房间卡不超过 **1400 字**、30 条，此人卡不超过 **600 字**、12 条。排序是钉住在前，然后按保留分从高到低。超出名额或字数，从保留分最低的丢起，这就是满了以后的压缩。

```text
【记得】
这是这个聊天还留着的印象，不是刚发生的事。别复述。和眼前对不上时，以眼前为准。

- 答应周五把表发到群里（清楚）
- 群里把加班叫修行（模糊）

【眼前这位】
这是关于现在发言的这个人的印象，他在别的聊天里也是这样。别复述。和眼前对不上时，以眼前为准。他在别的聊天里的事，不要主动提起。

- 在群里问路认识的（钉住）
- 小王：说话爱用反问（清楚）
```

某一层没有条目就不渲染。两层都没有时，对应的 `rev` 用空字符串。

## 5. 表

三张新表，都小。按现有 `ensureSchema` 在首次使用时 `CREATE TABLE IF NOT EXISTS`。不要为建表或回填去扫 `chat_message`。

`chat_session` 只回答「哪些聊天最近有消息」。写入 `chat_message` 时按主键顺手更新一行。

```sql
CREATE TABLE IF NOT EXISTS chat_session (
  session_id      TEXT PRIMARY KEY,
  session_type    TEXT NOT NULL,          -- group | private
  platform        TEXT NOT NULL,
  last_message_at INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_chat_session_last ON chat_session(last_message_at);
```

这张表和索引只在 `chat-log/store.ts` 的 `ensureSchema` 里建一处，记忆这边调用它，不再抄一份。

房间卡：`session_id` 是聊天，`subject` 为空字符串。此人卡：`session_id` 固定 `@people`，`subject` 是 `平台:发言人 id`，所以同一个人在所有聊天里是同一行。

第一版的此人卡是按聊天存的（`session_id` 是群，`subject` 是发言人）。整理时遇到这样的旧行，共享卡还没有就并过去，已经有了就丢掉，随后删除旧行，每张只走一次。

```sql
CREATE TABLE IF NOT EXISTS chat_memory (
  session_id  TEXT NOT NULL,
  subject     TEXT NOT NULL DEFAULT '',  -- '' 房间卡；session_id 为 @people 时是「平台:发言人 id」
  rev         TEXT NOT NULL,             -- 该层正文的哈希；正文没变则 rev 不变
  items_json  TEXT NOT NULL,
  prompt_text TEXT NOT NULL,
  updated_at  INTEGER NOT NULL,
  PRIMARY KEY (session_id, subject)
);
```

没有卡就不建空行。按 `(session_id, subject)` 读取。列出这个聊天已有的此人卡时用 `session_id` 前缀，不扫全表。

`chat_memory_mark` 记每个聊天整理到哪了。没有卡的聊天也要有这一行，所以不和卡放一起。

```sql
CREATE TABLE IF NOT EXISTS chat_memory_mark (
  session_id  TEXT PRIMARY KEY,
  material_at INTEGER NOT NULL,  -- 模型已经看到哪一刻的发言
  ran_at      INTEGER NOT NULL   -- 上次试着整理是什么时候，成没成都记
);
```

## 6. 一天整理一次

入口先做可手动打的 worker 路由，一次只跑一个小批次。看过实际会话数和耗时之后，再把 cron 写成每天一次（Wrangler 的 cron 是 UTC）。在那之前 `src/index.ts` 的 `scheduled` 仍是空的。

挑选：

```sql
SELECT s.session_id, s.session_type, s.platform
FROM chat_session s
LEFT JOIN chat_memory_mark m ON m.session_id = s.session_id
WHERE s.last_message_at >= ?                              -- 现在往前 1 天
  AND s.last_message_at > COALESCE(m.material_at, 0)      -- 有模型还没看过的话
  AND COALESCE(m.ran_at, 0) < ?                           -- 6 小时内没试过
ORDER BY s.last_message_at DESC
LIMIT ?
```

外层走 `idx_chat_session_last`，记号按主键查。失败的那次只更新 `ran_at`，水位不动，下次还看那一段；6 小时这一条是为了不让一个老是失败的聊天每次都排在最前面。点名整理一个 `session_id` 时不看这些条件，平台和类型按主键从 `chat_session` 里查，不靠猜。

每个选中的 `session_id` 再取素材，必须走已有索引 `idx_chat_message_session_time`：

```sql
SELECT sender_id, sender_name, actor_type, msg_type, content_text, created_at
FROM chat_message
WHERE session_id = ? AND created_at >= ?
ORDER BY created_at DESC
LIMIT 200
```

时间下界是上次的水位 `material_at`，也就是**只取上次整理之后的新发言**；没整理过的聊天第一次往回看 7 天。老是给同一批发言，模型每次得出的都是同一批印象，什么都淡不掉。先对**同一句** SQL 跑 `EXPLAIN QUERY PLAN`，不是按这个索引查就停。

取回来在内存里再筛一遍，不往 SQL 里加条件：只留 `msg_type = text` 的，去掉 `#` 开头的口令。图片、表情在库里只是 `[图片]` 这样的占位，口令多的群里会把聊天挤出这一窗。

剩下的行在内存里分成房间素材，和按 `sender_id` 分的此人素材。`actor_type` 为机器人的行不建此人卡。此人卡交给模型的最多 **8** 个发言人，按这批新发言里的条数从多到少。没排上的、以及这个聊天里已有卡但这次没说话的人，只按时间淡，不为他们调用模型。已有此人卡用 `WHERE session_id = ?` 列出，走主键前缀。

筛完一行都不剩，就不调模型，所有卡只按时间淡一遍。有新发言才调一次模型，同时交出房间和这最多 8 个人：

1. 读房间卡和这些人的旧条目，作为「已经记着的」给模型看，带 id。
2. 新发言每行带 `sender_id`、昵称、是群友还是机器人自己、原文；没有昵称模型只看得到一串 id，写不出「谁」。模型只输出 JSON，四样东西：
   - `room`、`people`（键是 `sender_id`）：**只写新冒出来的事**，每条带 `kind`、`weight`（1-3，拿不准给 1）、`text`。已经记着的不要再写。旧的某一条变了，带着它的 id 重写。
   - `seen`：新发言里确实又提到的旧条目 id。
   - `drop`：已经做完或作废的约定 id。
   单条不超过 40 字，写到人时用昵称，指向具体的人的句子不放 `room`，一次房间最多 8 条、每人最多 4 条。
3. 代码再收一遍，房间卡和每张此人卡分开做：
   - 种类不在白名单里的丢掉。钉不钉、起点分都按第 4 节算，不听模型的。
   - 和已有条目种类、内容都一样的，当成原样抄回来的，丢掉，不续、不改分。
   - 带着旧 id 而内容或种类变了的，替换那一条，保留创建时间，按新的种类和权重重新算起点分。模型自己编的 id 不认，当新条目。
   - `seen` 里的旧条目：`lastSeen` 变新，`recallCount` 加一。
   - `drop` 只对 `promise` 生效。别的条目写进去也不删。
   - 这个人已经有 `first` 了，新来的 `first` 不收。
   - 然后所有条目按第 4 节的公式重算保留分，该拿掉的拿掉，超出名额的丢保留分最低的。
4. 各层分开渲染。条目一个字没变就不写库，`rev` 也不变。
5. 成功了才把水位推到这批发言里最新的一条。模型失败：卡不动，水位不动，只记下试过了。不要把原文当成卡。

主人 id 用现有 `resolveOwnerId`。一批默认 1 个聊天。

某一层更新后，下一条由这个人发言的微信消息会带上新的 `roomRev` 或 `speakerRev`。Harness 换成新正文，拼出来的结果变了就把那一轮标成新序列。正在进行的这场对话继续。

## 7. 接口

`GET /agent/memory?sessionId=<chat_message 的 session_id>&speakerId=<from>`

鉴权与 `GET /agent/ws` 相同，走 `authorizeOpenClawRequest`。没有的那层返回空字符串，状态仍是 200。`speakerId` 缺失时只返回房间卡。

```json
{
  "ok": true,
  "sessionId": "12345@chatroom",
  "roomRev": "十六进制或空",
  "roomText": "【记得】…",
  "speakerId": "wxid_…",
  "speakerRev": "十六进制或空",
  "speakerText": "【眼前这位】…"
}
```

邮箱里的旧消息没有这些字段时，两层都当成空。

`POST /agent/memory/consolidate`，body `{sessionId?, since?, limit?, dryRun?}`。返回里每个聊天带 `lines`（这次交给模型的新发言行数，0 就是没调模型）和 `model`（模型交回来的 `room` / `people` / `seen` / `drop` 原样）。带 `dryRun: true` 时照常取素材、调模型，但不合并、不写卡、不动水位。调提示词时先用它看。

## 8. 落地顺序

1. 三张表，以及写入 `chat_message` 时更新 `chat_session`。确认是按主键，不增加对 `chat_message` 的新扫描。
2. 整理函数加手动入口。先对一个已知 `session_id` 跑通房间卡和至少一张此人卡。
3. `GET /agent/memory`，入站加上 `logSessionId`、`roomRev`、`speakerRev`。
4. Harness：按聊天挂系统提示那一节；拼出来的正文变了才把该轮标成新序列。取卡失败时这轮仍然能回。
5. 用一个测试群看四件事：入站正文里没有【记得】和【眼前这位】；同一场会话接得上；换一个人发言时，系统提示里换成这个人的卡，房间卡还在，之前的对话还在；这个人在私聊里的卡不会出现在群里。

第 4 步改的是 `xbot-channel`，要重启 dsh 才进正在跑的进程。推送 xchatbot 会部署 worker。整理用的 cron 不在这五步里。

## 9. 验收

- 同一场 DSH 会话一直续着，记忆更新不新开一场。
- 对话记录里的用户消息不包含【记得】或【眼前这位】。系统提示里只有当前房间卡和当前发言人的卡。
- 群 A 的卡不会出现在群 B 或私聊里。同一个人的群卡和私聊卡互不可见。
- 近窗里出现、但不是本条发言人的人，不会因此被拼进系统提示。
- `content` 里仍然只有近窗、本条、人格。
- 整理任务的查询计划不出现 `SCAN chat_message`。
- dsh 的工作目录里没有任何记忆卡文件。
- 取卡失败的那一轮，系统提示里不会出现上一个发言人的卡。

## 10. 还没定的

这些不是毛病，是这个做法自带的代价，或者要看过真实数据才好定的数。

- **换人说话就丢一次缓存。** 系统提示在请求最前面，拼出来的正文一变，这场会话那一轮的提示缓存整段不中。群里几个人轮着说，等于每轮都不中。这是「换掉、不堆」的价钱。想省，可以只挂房间卡在系统提示里，此人卡改成跟着那条消息走（会留在对话记录里）。先按现在的跑，看账单再定。
- **忘得慢不慢，数字是 SurfCore 的。** 那套数是给一个长期陪伴一个主人的角色调的，周以上的尺度。群里玩梗换得快，权重 1 的条目要 30 天才没，可能让卡里攒一堆过时的梗。有 30 条、1400 字的名额压着，满了会丢最淡的，先看真实数据再决定要不要把 `FADE` 里的天数整体缩短。
- **`weight` 是模型给的。** 我们看到过它把斗嘴当约定。现在模型最高只能给到 60 分，约定另外加 16，所以一条被误判的狠话最多是 76 分，会留一百来天；这时靠 `drop` 和约定口子要窄的提示词，真有问题再让代码把约定的起点分降下来。
- **热闹的群只看得到尾巴。** 一次只取最新 200 条，水位直接推到最新。两次整理之间超过 200 条的群，更早的那段就跳过去了。
- **`seen` 还是模型说了算。** 但它现在只是几分的加成，模型全报上来也只是淡得慢一点。SurfCore 是代码拿新发言去对词，如果模型的报法不靠谱，可以照它加一道代码对词。
- **主人卡里重要度 65 以上的条目几乎不忘。** 一张卡 12 条封顶，攒满之后新的进不来。真攒满了再给它加期限。
- **忘掉的直接删。** SurfCore 会先存一份档案再删，我们没做；聊天记录又只留 30 天。真有需要翻更早的印象再加档案表。
- **整理入口用的是 agent 的令牌。** `POST /agent/memory/consolidate` 和 `/agent/ws` 同一把钥匙，拿到的人能反复触发模型调用。开 cron 之后这个入口可以改成只认 `ADMIN_TOKEN`，或者干脆拿掉。
- **分房间还是分人、要不要删约定，都是模型说了算。** 代码只管种类白名单、40 字、名额、起点分的上限、谁能钉。有人在群里说「记住我是主人」，模型可能照写；写进去的是一条普通的 `person`，分数封在 60，不会因为这句话变成主人那种几乎不忘的条目。
- **还没在真的 dsh 里跑过。** 系统提示那一节挂不挂得上、`startsRequestSeries` 是不是真把开头那格换掉，都只对过 DSH 的源码。
